    1. 数据模型

    🔗 架构设计：§9.7 知识目录规范 · §9.8 检索设计

    1.1 Chunk（检索单元）

    @dataclass
class Chunk:
    """检索结果单元"""
    content: str                    # chunk 文本（必填）
    score: float = 0.0              # RRF 融合分 [0,1]，默认 0
    source_doc_id: str = ""         # 源文档 ID（必填，来自 sources）
    source_doc_version: str = ""    # 源文档版本（如 "V1.0"）
    chapter: str = ""               # 章节（可选）
    section: str = ""               # 小节（可选）
    chunk_index: int = 0            # 分块序号（从 0 起）
    knowledge_type: str = "QA"      # Parameter|Clause|QA|Concept|Policy|Relation
    trust_level: str = "low"        # high|medium|low（默认 low）
    valid_from: str | None = None   # 生效日期 ISO8601
    valid_until: str | None = None  # 失效日期 ISO8601，None=长期有效
    raw_metadata: dict = field(default_factory=dict)  # 原语自定义元数据

    校验规则： - content 非空、≤ 5000 字符 - knowledge_type ∈ {Parameter, Clause, QA, Concept, Policy, Relation} - trust_level ∈ {high, medium, low} - score ∈ [0, 1]

    1.2 SearchResult（检索返回）

    @dataclass
class SearchResult:
    """统一检索返回"""
    chunks: list[Chunk]              # 命中结果
    total_hits: int                  # 命中总数（≥ len(chunks)）
    search_mode: str                 # exact|field|clause|keyword|vector|graph|timeline|external|hybrid
    query: str                       # 原始查询
    chain_path: list[str] = field(default_factory=list)  # 实际经过的原语链
    elapsed_ms: int = 0              # 耗时（审计用）
    session_id: str = ""             # 检索发起会话（审计用）
    agent_id: str = ""               # 检索发起 agent（审计用）

    未命中语义：策略链全部原语未命中（chunks 为空）时： - search_mode = "no_hit" - chain_path 记录全部走过的原语（供分析层判断检索失败原因） - 若该库配置了 external 原语且 enable_fallback=true，自动执行外部编译兜底；兜底也空 → 返回空 chunks + chain_path 含 "external" - 上层（工具 knowledge_search）收到空结果时，返回"未检索到相关知识，建议换措辞或调整知识库"的提示语

    1.3 Freshness（生命周期状态）

    @dataclass
class Freshness:
    """文档生命周期状态"""
    doc_id: str                      # 文档 ID
    status: str                      # active|superseded|expired|unknown
    valid_from: str | None = None    # 生效日期
    valid_until: str | None = None   # 失效日期
    checked_at: str = ""             # 检查时间 ISO8601
    reason: str = ""                 # 失效原因（如 "ESB docStatus=1"）

    Freshness 是生命周期检查的统一产物，lifecycle 是可扩展机制：reason 为开放式字符串，可承载任意失效来源（文件 mtime / ESB docStatus / DB 版本 / 消息队列等）。内置三种检查器——FileLifecycleChecker（mtime 30s 轮询）、EsbLifecycleChecker（ESB docStatus 事件）、NoneLifecycleChecker（不自动失效）。新增一种 lifecycle = 三步（与 DocStructPlugin / 检索原语同为"注册即用"）：①实现 check_freshness 检查器；②§5.1 schema 的 lifecycle enum 加值；③注册中心加载器补 值 → 检查器 映射。RAGProvider.check_freshness()（§2.2）内部按 lifecycle 值分发到对应检查器。

class StructuredBlock:

    knowledge_types 用途（知识类型白名单）：

    • 取值：全局六类枚举 Parameter | Clause | QA | Concept | Policy | Relation（与 frontmatter type 一致，§1.1 / 架构 §9.7.2），每库声明自己的子集
    • 生效时机：入库流水线 L2 插件产出 StructuredBlock → 映射 type → 生成 OKF 文件前校验 type ∈ knowledge_types（ingest_pipeline.py 调用 validate_knowledge_type）；不在名单内则拦截（不写 wiki/，不建索引）
    • 与 struct_plugin 分工：插件管"怎么切"（识别结构块），白名单管"能存什么"（校验 type）；插件可识别出多种类型，白名单决定该库实际收纳哪几种
    • 注册中心加载器在启动时校验该字段值合法（enum 范围内），非法配置抛 RegistryValidationError

    embedding 用途（入库侧向量化开关）：

    • true：L3 调用 embedding 模型（provider 指定的向量库 + embedding_model/embedding_dimension，§6.1）生成向量并写入 ES 向量索引；检索链可含 vector 原语做语义兜底
    • false：L3 只生成 OKF 文件，不调 embedding、不写 ES 向量；检索链不含 vector，靠精确/字段/图谱命中
    • 判断标准：含自由文本（Concept/Policy/QA/Clause）且提问开放式（措辞不可枚举）→ true；纯结构化（Parameter/Relation 为主）且业务问题可精确命中 → false
    • 与检索链一致性：true 配含 vector 的 retrieval_chain；false 配不含 vector 的链（若链含 vector 而 embedding: false，属"预留未启用"状态，启用前应改为 true）
    • 编码要点：ingest_pipeline.py 的 vectorize_and_index() 依据该开关决定是否调用 embedding 与写 ES

    🔗 架构设计：§9.9.1 入库流水线

    async def ingest_pipeline(
    doc_path: str,
    kb_id: str,
    registry: KnowledgeRegistry,
    plugin: DocStructPlugin | None,
    rag_config: RagConfig,
) -> str:
    """四层流水线。失败保留旧索引并告警。"""
    doc_id = generate_doc_id(doc_path)               # 基于内容 hash

    # L0 文档解析（复用 AgentScope 2.0 readers / PyMuPDF / MinerU）
    raw_text = await parse_document(doc_path)

    # L1 通用切块
    chunks = split_semantic_chunks(
        raw_text,
        max_chars=rag_config.max_chunk_chars,        # 1500
        overlap_ratio=rag_config.chunk_overlap_ratio, # 0.1
    )

    # L2 业务结构化（插件化）
    blocks = plugin.structure(chunks, doc_id) if plugin else []
    fields = plugin.extract_fields(blocks) if plugin else []

    # L3 向量化 + 索引
    await vectorize_and_index(doc_id, chunks, blocks, fields)

    # 生成 OKF 知识文件 + 更新 sources.json + 构建图谱
    await write_okf_files(doc_id, blocks, fields)
    await update_sources_registry(doc_id)
    await build_graph(doc_id, blocks)

    return doc_id

    def compute_risk_level(entry: KnowledgeEntry) -> str:
    """返回 high / medium / low。规则判定，不调 LLM。"""
    if entry.knowledge_type == "Parameter" and entry.trust_level == "low":
        return "high"
    if not entry.sources or not entry.source_doc_id:
        return "high"
    if entry.trust_level == "low":
        return "high"

        return "medium"

    第一部分 问题与设计理念

    9.1 这一章要解决什么问题

    一句话：让银小帆能基于组织的真实文档回答问题，而不是"凭记忆"编造。

    银小帆需要"知识"

    员工问银小帆"运作指引对投资比例有什么要求""SET829 的管理费率是多少""同管理人还有哪些产品"——这些问题不能靠模型预训练知识回答，必须基于真实的业务文档（法规、合同、操作指引）来回答。

    设计理念：基于 OKF（Open Knowledge Format）

    本知识库的整体设计基于 OKF（Open Knowledge Format）——Google Cloud 于 2026 年 6 月发布的开放知识格式标准。OKF 把 Karpathy 的 LLM Wiki 模式标准化为"一组 Markdown 文件 + YAML 元数据"，核心思想有三条，本章全部落地：

    OKF 理念含义本章落地
    文件为规范形态知识是 Markdown + YAML 文件（可打开、可审查、可版本管理），向量库/RAG 只是消费者而非知识本体§9.7 知识目录规范（frontmatter 携带来源/时效/可信度）
    生产者/消费者分离知识不锁在某个 Agent/框架/向量库里，任何人可生成、任何模型可消费同一份知识产物§9.10 知识库工作台（Agent 生产 → 业务人员审查 → 银小帆消费）
    知识可信度每条知识可追溯"谁生成、来自什么来源、现在是否仍有效"，Agent 用知识前先判断是否值得信§9.9 信任与生命周期治理（来源绑定/人工确认/trust_level）

    OKF 并不替代 RAG/向量库/搜索引擎——它只定义这些系统共同操作的知识产物长什么样。本章"多原语组合检索"（§9.4）正是在 OKF 文件之上叠加检索能力，两者不冲突：OKF 管知识怎么存，RAG 管知识怎么查。

    一句话概括本设计：以 OKF 文件为知识本体，以多原语检索为查询手段，以 Obsidian 和 Web 服务为人工界面，以注册中心为全局治理——让托管业务知识成为银小帆多智能体共享、业务人员可审查的组织级资产。

    • 向量是稀缺能力——仅需求管理专员用 ES 向量，其余 6 套停在关键词层
    • 业务人员无统一入口——人审三态（pending→confirmed）仅法律法规一家有
    • 知识格式不统一——各知识库 frontmatter 字段各异
    • 无统一权限——各专员知识库无文档级权限控制

    9.3 问题分析：为什么不直接用向量 RAG

    "文档切块 → 向量化 → 向量库检索"够吗？

    不够。原因有三个：

    ① 知识变成黑盒

    文档一旦向量化，就锁在向量库里。业务人员打不开、看不了、改不了。知识是否准确、是否过时、来自哪个文档——全都不可追溯。在金融合规场景这是致命的：回答错了要担责，必须能溯源。

    ② 结构化参数不该向量化

    费率、风险等级、开放日是精确数值，用向量检索是错误工具——"管理费率 0.5%"应该精确匹配，而不是"语义相似"。合同协议专员用字段注册表精确匹配，完全不需要向量。

    ③ 没有变更感知

    需求管理专员的 ES 向量库，文档更新要手动触发 bulk_ingest()。源文档改了，向量库还是旧的——知识 silently 过时。

    那纯文件式呢？

    也不行。合同协议专员遵循 LLM Wiki 模式（wiki_manager.py 头注释"遵循 Karpathy LLM Wiki 模式"）——有文件 + BM25 + 图谱 + 生命周期，但检索层没有"向量语义检索"（无 embedding/向量库）。

    要澄清的是：LLM Wiki 的"语义理解"来自 LLM 本身（模型推理时知道"监督≈限制"），而非检索时的向量匹配。它的语义能力发生在检索之后（靠 LLM 读内容后理解），检索本身仍是字面匹配（精确/BM25/图谱）：

    用户问"投资监督条款是什么"
  → 字段/BM25 字面匹配 → "监督"与"限制"字面不同 → 查不到
  → 抛给文档LLM检索（外部 LLM 读 PDF）→ 此时才靠 LLM 语义理解作答
     ↑ 检索阶段无向量匹配，语义理解全靠检索后的 LLM

    后果：开放式问答（措辞千变万化）在检索阶段的召回率低——"投资监督"查不到"投资限制"，就得依赖文档LLM检索（黑盒）兜底，返回内容不可追溯。

    现有代码证明：两者互为反面

    文件规范 + 生命周期向量语义检索
    合同协议专员✅ 有❌ 无 → 检索阶段字面匹配，语义靠文档LLM检索兜底
    需求管理专员❌ 无✅ 有 → 更新靠手动，无治理

    结论：纯向量或纯文件都不行。最优解是"以合同协议专员的多原语架构为骨架，把向量检索作为可供各库按需启用的原语"——各库在注册中心声明自己的检索策略链（retrieval_chain），需要语义检索的库启用 vector 原语（如合同协议补 vector 提升开放式问答召回、需求管理已用 vector），不需要的库不启用。

    核心理念：知识以文件为规范形态（可审查、可迁移、可治理），向量索引是派生的检索层（可从文件重建）。多种检索原语按知识类型组合，不一刀切。

    9.6 全 Agent 知识库统一治理

    核心：前几节解决"单个知识库怎么做"，本节解决"所有知识库怎么统一管"——让任何子 agent（含知识问答专员、业务 agent）都能检索任何有权限的知识库。manager 只做路由（意图识别 → 分配到能检索的子 agent），本身不执行检索。

    embedding 何时 true / 何时 false：embedding 是入库侧开关——true 则 L3 调用 embedding 模型生成向量并写入 ES 向量索引（检索链可含 vector 原语做语义兜底）；false 则 L3 只生成 OKF 文件、不调模型、不写 ES 向量（检索链不含 vector，靠精确/字段/图谱命中）。判断标准：

    条件embedding: trueembedding: false
    命中方式语义（"清算接口怎么调"命中 POST /api/clear）精确/结构（费率 0.5%、条款编号、字段名）
    知识类型含自由文本（Concept / Policy / QA / Clause）纯结构化（Parameter / Relation）为主
    提问方式开放式（措辞千变万化，不可枚举）固定问法（查费率、查编号）
    检索链含 vector 原语不含 vector 原语
    代价L3 调模型 + 写 ES 向量不调模型、不写 ES，更省

    选 true（任一满足）：①知识含自由文本（Concept/Policy/QA）；②用户提问措辞 ≠ 文档原文；③检索链需要 vector 原语做语义兜底。选 false（需同时满足）：①知识以 Parameter（数值/枚举）+ Relation（图谱）为主；②业务问题都能用精确匹配/字段/条款编号命中；③不需要语义泛化兜底。

    与检索链的配合：embedding 与 retrieval_chain 是否含 vector 应保持一致——true 配含 vector 的链；false 配不含 vector 的链。注意：合同协议目前 embedding: false 但链含 vector（§9.4.4 P5 计划补向量），属"预留未启用"状态，启用前应把 embedding 改为 true。

    文档实例：研发支持（true，API 语义检索）、法律法规（true，概念/QA 自由文本）、合同协议（false，78 字段 + 条款切分已足够结构化）。

    permission / tenant / owner —— 知识库的三层归属：三个字段回答"这份知识库归谁管、谁能看、谁负责"，共同构成访问与治理的归属声明：

    字段问题控制案例值
    permission谁能查访问白名单（角色/会话过滤）[rnd_group] 研发团队
    tenant归哪个部门隔离边界（租户/部门归属）rnd_dept 研发部
    owner谁负责维护治理归属（归属 agent）技术支持专员

    ① permission —— 谁可以访问这个库：检索时按会话/用户角色过滤，permission 为空 = 公开，非空 = 只有命中的角色能查。配合 §9.11.2 构成多层过滤：

    permission（库级）      → 谁能进这个库
rag_doc_whitelist（文档级）   → 进库后看哪些文档
rag_trust_level_min（可信度） → 低权限会话看不到未确认知识
rag_relation_whitelist（图谱）→ 哪些关系可查

    案例 [rnd_group]：只有研发团队会话能查该库 API 知识，其他部门问不到。

    ② tenant —— 数据隔离边界：比 permission 更粗的一层租户隔离——同一套系统多个部门（研发部/托管部/风控部），各部门知识库分属不同 tenant，默认跨租户不可见（防部门间数据泄露）。与 permission 是两层门：

    维度permissiontenant
    粒度细（角色/会话）粗（部门/租户）
    过滤时机检索时按角色注册中心发现/路由时按租户
    类比"谁能进这栋楼""这栋楼属于哪个园区"

    实际顺序：先 tenant 决定"这个部门能不能看到这个库"，再 permission 决定"这个角色能不能查内容"。

    ③ owner —— 归属 agent（谁维护）：治理归属而非访问控制——指定哪个业务 agent 负责该库的日常维护（入库、答疑、知识更新）。案例中与②步骤呼应：第②步新建的「技术支持专员」就是这个库的 owner——登记声明"库归谁"，②步骤把"谁"建出来。owner 的三大作用：

    1. 路由归属：用户提问 → manager 按 domain + owner 路由给对应专员
    2. 治理报表归属：注册中心规模/质量/健康度报表按 owner 聚合（谁负责的库表现如何）
    3. 责任追溯：知识有问题找 owner（配合 §9.9.3 审计的审查记录）

    三者关系一句话：tenant 决定"哪个部门能看到这个库"（隔离边界），permission 决定"哪个角色能查内容"（访问白名单），owner 决定"哪个 agent 负责维护"（治理归属）——一个管"看得到吗"，一个管"能查吗"，一个管"谁负责"。

    六类知识类型（type）的区别

    type 是知识文件的第一分类维度，回答"这份知识是什么"，与 wiki/ 下的子目录一一对应。六类的区别取决于三个维度：是否可精确匹配的数值/字段（决定用不用向量）、是"知识本身"还是"知识之间的关系"、怎么生成的（编译切分 / 自学习 / 图谱构建）：

    类型wiki/ 子目录是什么案例检索方式
    Concept 概念concepts/名词解释、术语、流程"什么是清算流程"词法 + 向量（语义）
    Policy 政策/规则policies/制度、规则、监管要求"运作指引对投资比例的要求"词法 + 向量
    Parameter 结构化参数parameters/可精确匹配的数值/枚举费率 0.5%、风险等级、开放日精确匹配（不向量化）
    Clause 条款clauses/合同中可切分的条款"第三条 管理费率"编译切分 + 字段精确 + BM25 + 向量混合
    QA 问答对qa/一问一答的知识沉淀"清算法怎么开通？→ 步骤…"缓存 + 词法 + 向量
    Relation 关系relations/实体之间的关系管理人 A ↔ 产品 B（同管理人）图谱检索（不向量化）

    与 §9.4.1 三种检索策略的关系（按检索方式分 vs 按内容形态分，两者不冲突）：

    检索策略（§9.4.1）覆盖的 type
    结构化参数 → 精确匹配Parameter
    半结构化条款 → 切分 + BM25 + 向量Clause
    自由文本问答 → 向量 RAG + BM25Concept / Policy / QA
    （图谱）→ 关系检索Relation

    最直观的分辨方法——按顺序问：

    1. 它是一个数值/枚举吗？→ Parameter
    2. 它是一条合同/法规条文（有编号可切）吗？→ Clause
    3. 它是实体之间的关系吗？→ Relation
    4. 它是一问一答形式吗？→ QA
    5. 它是名词/术语的解释吗？→ Concept
    6. 否则是政策/规则条文→ Policy

    与 knowledge_types 白名单的关系（§9.6.3）：每个知识库在注册中心声明自己的 type 子集，入库生成 OKF 文件时校验 type ∈ knowledge_types——不在名单内的类型被拦截，保证"库只存该存的"（如合同协议库只存 Parameter/Clause/Relation，不存 QA/Policy）。

    9.8 检索设计

    检索原语与统一入口

    所有知识库检索统一走 RAGProvider。但检索不是"固定 8 种原语 + 统一降级链"——而是检索原语接口通用，检索策略（用哪些原语、什么顺序）由每个知识库在注册中心声明：

    检索原语（通用接口，8 种）—— 每种原语是"一种检索动作"
    ↑ 各库可按需实现/启用（不是所有库都有全部原语）

检索策略（每库声明）—— 用哪些原语、什么顺序、什么阈值
    knowledge_registry.yaml 声明 retrieval_chain
    ↑ 每库一条策略链，不再统一

降级执行（通用引擎）—— 按该库策略链顺序逐级尝试，命中即返回
    RAGProvider.search() 读策略，执行对应原语

    检索原语接口：

    """检索原语：一种检索动作。各库可按需实现/启用。"""

    async def retrieve(self, query: str, **kwargs) -> list[Chunk]:

    RAGProvider 核心方法（统一入口 + 生命周期，检索动作由原语承担）：

    方法用途
    search(query, knowledge_base)统一入口：读该库 retrieval_chain，按序执行原语，命中即返回

    check_freshness / invalidate生命周期检查 / 标记失效

    检索策略链（每库声明，非全库统一）

    关键修正：原先的"六级检索降级链"是 contractQ 这一种库的实例，不是全库统一。各库的实际检索路径本就不同（法律法规五级漏斗、客户三轮 Jaccard、稽核关键词+SQL），因此降级链改为每库在注册中心声明的检索策略链：

    知识库retrieval_chain（检索策略链）原语实现
    合同协议cache → field → clause → keyword → vector → graph → timeline → external现有全套 7+1 种
    法律法规cache → keyword(TF-IDF) → concept → entity → article → raw_lookup五级漏斗 + raw 定位
    稽核风控keyword → sql关键词评分 + OceanBase
    客户问答cache → jaccard → substring三轮降级
    需求管理keyword → vectorES 混合检索
    舆情keyword → fingerprint关键词 + 指纹去重
    产品参数cache → wiki → oracle复用共享 Wiki

    各检索原语的含义与实现差异：

    原语接口含义（通用）各库实现差异
    cache问答缓存命中通用（hash + 自学习归档）
    field字段精确检索合同：78 字段；法规：条款号
    clause结构化条目检索合同：条款；法规：条文；客户：问答对

    • 原语可选择性启用：graph/timeline/external 只有对应能力的库才在链上（合同全有，客户只有 cache/jaccard/substring）
    • 顺序是策略而非定式：合同场景"词法先于向量"（命中率高、延迟低），其他库可不同
    • chain_path 记录实际路径：供分析层做质量分析（无论策略链多长，执行后记录实际走过的原语）

    frontmatter 字段Obsidian 呈现业务人员的作用
    type页面属性区（Properties）一眼看出"条款/参数/问答"

    sources显示来源文档 ID，点击跳转追溯来源：打开原文核对

    1. 打开 vault → 看"待审查队列"页（Dataview 自动列出 pending 知识）
2. 点击一条 → 知识正文 + frontmatter 渲染的属性区

    9.11 集成与权限

    集成方式：工具为主 + Context 注入为辅（双轨）

    核心决策："Agent 怎么拿到知识"不是"工具还是注入"二选一，而是按需检索走工具（可审计、省 token），高频必用走注入（零延迟、模型必用）。

    ① 工具注册（主，问答场景）——检索统一收敛为单一入口，原 graph/field/timeline 不再是独立工具（它们已是 search() 内部原语，由策略链自动路由）：

    工具用途
    knowledge_search唯一检索入口：读该库 retrieval_chain，按序执行原语（cache→field→clause→keyword→vector→graph→timeline→external），命中即返回
    knowledge_ingest入库（走四层流水线 §9.9.1；管理操作，非问答）
    knowledge_review_status待审查队列查询（业务人员/运维用）

    ② Context 注入（辅，高频场景）——复用 AgentScope 2.0 的 Context middleware，固定注入：

    注入内容场景理由
    manager 路由模板每次意图识别必用、零延迟
    会话高频产品参数产品专员对话反复用，省一次工具调用
    会话级白名单知识会话绑定知识固定可见性

    ③ 适用场景划分：

    知识类型注入方式理由
    用户明确提问的知识工具检索省 token、可审计
    manager 路由模板Context 注入每次必用，固定注入零延迟
    会话高频产品参数Context 注入省一次工具调用
    文档类深度问答工具检索内容多，注入爆上下文，按需取 chunk
    待审查/管理操作工具检索运维场景，不注入

    与 AgentScope 2.0 的关系：工具注册用其 Toolkit（项目已在用），固定注入用其 Context middleware，两者互补不冲突。

    第 ③ 步：实现 DocStructPlugin（§9.4/§9.9.2 插件机制）

    插件机制是什么：通用流水线（L0 解析 / L1 切块 / L3 向量化）对所有知识库都相同，但它不知道"哪几块拼起来是一个接口、一个表"。插件就是告诉系统"这份文档该怎么切成业务结构、切完抽什么字段"——把技术支持专员读文档时的专业眼光，写成一段代码交给流水线（入库 L2 环节调用）。通用流水线解决"所有知识都能被索引"，插件解决"每个领域知识都被正确理解"。

    定义插件只做三件事（对应三个方法）：

    方法管什么要回答的问题
    can_handle(doc_type)认领文档这份文档是不是我管的类型？
    structure(chunks)业务切分一堆通用块里，哪几块拼起来是一个接口/表？
    extract_fields(blocks)字段提取这个接口的 endpoint/参数、表的字段是什么？

    第一步：先看原始文档长什么样（决定 can_handle 和 structure）。《托管系统 API 手册.pdf》大致内容是：

    ## 清算接口
POST /api/clear
参数：fund_code, amount, order_id
返回：{ "code": 0, "data": { "status": "success" } }
说明：发起基金清算

    第二步：写 can_handle —— 认领文档

    def can_handle(self, doc_type):
    # 流水线按文档识别出的类型分发：文件名/首部含"API手册/接口"→ api_manual
    # 含"数据库设计/表结构"→ db_design；都不含 → 交给别的插件
    return doc_type in ("api_manual", "db_design")

    第三步：写 structure —— 把通用块切成"接口块/表块"。输入是 L1 切出的通用块，你要识别"一组的边界"，把相关块归并成一个 StructuredBlock：

    import re

def structure(self, chunks, source_doc_id):
    blocks = []
    current = None
    for chunk in chunks:
        text = chunk.content.strip()
        # 接口边界的标志：HTTP 方法开头（POST/GET/PUT/DELETE）→ 新接口开始
        if re.match(r'^(POST|GET|PUT|DELETE)\s+/', text):
            current = StructuredBlock(
                block_id=f"api-{len(blocks)+1:03d}",
                block_type="api_endpoint",
                title=text.split('\n')[0],        # "POST /api/clear"
                content=text,
                source_chunks=[chunk.chunk_index],
            )
            blocks.append(current)
        elif current is not None:
            # 紧跟在接口后面的行（参数/返回/说明）归入当前接口块
            current.content += '\n' + text
            current.source_chunks.append(chunk.chunk_index)
    return blocks

    关键思维：你写的不是"通用规则"，是你读这份手册时的眼睛——看到 POST /api/clear 就知道"新接口开始了"，看到下面几行就知道"这是它的参数"。插件就是把这双眼睛复制给系统。若文档是数据库设计（CREATE TABLE / 表名开头），同理识别"表块"边界。

    第四步：写 extract_fields —— 从接口块里抽可精确检索字段

    def extract_fields(self, blocks):
    fields = []
    for b in blocks:
        if b.block_type == "api_endpoint":
            first_line = b.content.split('\n')[0]
            method, endpoint = first_line.split(' ', 1)
            # 抽参数：匹配"参数：xxx, yyy"行
            m = re.search(r'参数[：:]\s*(.+)', b.content)
            fields.append(FieldValue(field_name="endpoint", field_value=endpoint.strip(), field_type="str"))
            fields.append(FieldValue(field_name="method", field_value=method.strip(), field_type="str"))
            if m:
                fields.append(FieldValue(field_name="params",
                                         field_value=[p.strip() for p in m.group(1).split(',')],
                                         field_type="list"))
    return fields

    第五步：把插件指向注册中心（第①步的 struct_plugin 字段）：

    struct_plugin: api_doc_plugin    # ← 就指向 ApiDocPlugin 这个类

    插件做完后系统怎么用：structure 产出的 StructuredBlock 变成 OKF 知识文件（第④步），extract_fields 产出的 FieldValue 注册成可精确检索字段——如 endpoint=/api/clear 进入字段索引，用户问"清算接口的参数"时 field 原语精确命中。

    "几十行"的真相：插件难的不是代码量，而是先回答两个问题——①这份文档里什么标志代表"一组"开始？（合同：第X条；法规：第X条；API：HTTP 方法+路径；DB 设计：CREATE TABLE/表名）→ 这是 structure 的切分规则；②业务问题会按什么字段问？（"清算接口怎么调"→按 endpoint；"有没有 openid 字段"→按字段名）→ 这是 extract_fields 抽什么。想清楚这两点，插件基本就是"正则 + 分组"几十行。

    对应关系：第①步登记的 struct_plugin: api_doc_plugin 即指向本步实现的插件——登记声明"入库用什么插件"，本步把插件实现出来，④ 入库时才可用。

    L3 向量化"体现在哪里"：向量化之后的"向量"并不出现在 vault 目录里——目录骨架里只有文件、没有向量文件。向量是派生的检索层，存放在外部向量库 ES：

    位置内容可否读
    vault 目录（文件为规范形态）wiki/clauses/api-001.md、sources.json✅ 可打开/审查/重建
    ES 向量库（派生检索层）api-001 → [0.0123, ...]（1024 维，DashScope text-embedding-v3）❌ 数字数组，只做相似度计算
    • 向量不落 vault 的原因：向量是数字数组，进目录会让知识变"黑盒"（§9.3.1①）；且向量可由 OKF 文件随时重建（§9.4.1"向量索引是派生的检索层，可从文件重建"）
    • 向量何时生效：第⑥步检索链走到 vector 原语时——用户问"清算接口怎么调"，cache/field/clause/keyword 字面未命中（"清算"≠"clear"），vector 原语把问题转向量与 ES 中 api-001 的向量算余弦相似度，语义命中
    • 开关：注册表 embedding: true 才启用向量化；填 false 则 L3 只生成 OKF 文件、不调 embedding、不写 ES 向量（纯结构化参数库适用）

    一句话概括：以 OKF 文件为知识本体，以多原语检索为查询手段，以 Obsidian 和 Web 服务为人工界面，以注册中心为全局治理——让托管业务知识成为银小帆多智能体共享、业务人员可审查的组织级资产。

    核心理念：采用 OKF（Open Knowledge Format）——知识以 Markdown + YAML 文件为规范形态（可审查、可迁移、可治理），向量索引是派生的检索层（可从文件重建）。
